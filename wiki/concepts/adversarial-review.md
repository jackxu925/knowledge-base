# Adversarial Review

> GStack 中的质量保障机制：模型以对抗性角色审视方案，自动发现和修复问题。计划的意义不再是写一份漂亮文档，而是让返工和风险尽量在动手前暴露。

---

## 定义

Adversarial Review 是一种让 AI 以"挑刺"角色审视方案的技术。不同角色的 agent 从不同角度攻击方案，暴露潜在漏洞，并尝试自动修复。

---

## 运作流程

```
方案生成 → 多角色对抗评审 → 自动修复 → 评分提升 → 剩余风险显性化
```

**案例**：报税工具方案

1. **初始方案**：Gmail + 浏览器自动化 + CPA 市场
2. **对抗评审发现**：
   - 没有失败处理
   - 没有隐私章节
   - 2FA 交接没有方案
3. **自动修复**：能补的自动补
4. **剩余问题**：不能补的留成后续问题，显性化记录
5. **评分变化**：6 分 → 8 分

---

## 评审角色

| 角色 | 视角 | 关注点 |
|------|------|--------|
| CEO | 商业 | 商业模式、市场规模、竞争壁垒 |
| 工程师 | 实现 | 技术可行性、性能、扩展性 |
| 设计师 | 体验 | 用户流程、可用性、视觉 |
| DevEx | 维护 | 代码质量、文档、可维护性 |
| Security | 安全 | 数据隐私、供应链攻击、权限 |

---

## 核心价值

1. **前置风险暴露** — 在写代码前发现问题
2. **自动修复** — 降低人类 review 负担
3. **显性化记录** — 让工程师知道接下来要盯住什么
4. **评分量化** — 从 6 分到 8 分，知道改进空间

> "我们的设计文档经历了两轮对抗性评审，并自动发现和修复了 16 个问题。"

---

## 与传统 Code Review 的对比

| 维度 | 传统 Code Review | Adversarial Review |
|------|-----------------|-------------------|
| 时机 | 代码写完后 | 动手写代码前 |
| 对象 | 代码实现 | 方案设计 |
| 角色 | 同事人工 review | 多角色 agent 自动评审 |
| 修复 | 人工修改 | 自动修复 + 人工确认 |
